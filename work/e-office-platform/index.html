Building modules on an enterprise e-Office platform

Approval workflows, dashboards, RTI, grievance, POSH, survey and training modules, plus UAT and regression cycles to keep them stable in production.

  • React
  • Redux
  • KendoReact
  • NewgenONE
  • REST

Context

A public-sector enterprise was modernising its staff-facing e-Office application. The new front end was built in React on top of workflow and document services, with NewgenONE as the underlying workflow platform, and covered the day-to-day administrative processes of a large organisation.

I worked on front-end development, API integration and testing across the platform's modules.

What I did

  • Built and maintained React modules for approvals, inbox and worklist, RTI, POSH, grievance, legal, TA/DA claims, training and survey, and the movement registry.
  • Used Redux Toolkit with asynchronous actions to integrate back-end APIs: login, queue identification, worklist retrieval, process definition queue IDs, work item retrieval and unlocking, and movement registry creation, retrieval and updates.
  • Built dynamic approval information displays, dashboard cards and charts, and KendoReact Grid interfaces with pagination.
  • Integrated RTI forms and notesheet downloads.
  • Customised the Kendo rich text editor and built reusable components with styled-components.
  • Prepared the software requirements specification for the POSH and grievance portals.
  • Led UAT and regression testing cycles and wrote the testing documentation later used to onboard new testers.
  • Took part in builds and deployments.

What went wrong and how it was found

Production defects turned up across authentication, document rendering and enterprise configuration. The pattern for each was the same: reproduce it, find which layer it belonged to, fix it if it was ours, and document it if it was not. Some issues needed coordination with back-end developers on API behaviour, and some with the infrastructure team on deployment dependencies.

One recurring category was data display: grids and approval views that showed something other than what the underlying process held. Those were resolved by tracing the API responses rather than adjusting the UI.

What I learned

An e-Office platform is a set of business processes first and a set of screens second. Writing the requirements specification for two of the portals, and then testing the workflows I had built, made the business rules much clearer than building the UI alone would have.
