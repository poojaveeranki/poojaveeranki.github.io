Reviewing a disaster-recovery design for Intelligent Viewing

Identifying gaps in the proposed DR setup, assessing VM-level replication, and estimating the setup work for the downtime window.

  • DR
  • HA
  • RabbitMQ

Context

A national financial institution ran the Intelligent Viewing platform across two production servers, with publisher workloads and RabbitMQ spread across them. A disaster-recovery site was being planned, and the first proposal mirrored only one of the two servers.

I reviewed the proposed design, identified the gaps, assessed the replication approach, and prepared the estimates for the setup work. Implementation of the infrastructure itself was coordinated with the infrastructure teams.

What I did

  • Mapped what actually ran on each production server and compared it with what the single DR virtual machine would cover.
  • Identified the need for a second DR virtual machine to host RabbitMQ and the second publisher workload.
  • Assessed whether VM-level replication with Nutanix LEAP could replace the file-level synchronisation that had originally been requested.
  • Identified the database and OTDS dependencies that had to be in place before Intelligent Viewing could come up on the DR side.
  • Prepared an activity-by-activity estimate for the Intelligent Viewing setup during the downtime window, and listed which teams were needed for each step.

What went wrong and how it was found

One DR server would not have matched production. With only one mirrored server, RabbitMQ would be a single point of failure, document conversion capacity would be roughly half of production, and the DR architecture would differ from the primary data centre. I wrote this up so the decision could be made with the trade-off visible.

Replication needed questions, not acceptance. Rather than accept the VM-level replication proposal as given, I prepared a clarification checklist covering replication in both directions, snapshot frequency and recovery point objective, application-consistent versus crash-consistent snapshots, network test failover, static IP assignment through the guest tools, failback, and the risk of a test environment conflicting with live systems.

Dependencies were not yet ready. The DR databases were not synchronised, synchronisation needed downtime, OTDS could not work without its database, and Intelligent Viewing depended on OTDS. The order of operations followed from that chain.

The estimate

| Activity | Estimated time | | --- | --- | | Publisher and RabbitMQ installation | 3 to 4 hours | | Publisher and RabbitMQ configuration | 1 hour | | Configuration changes on the replicated server | 1 hour | | Start services and inspect logs | 45 minutes | | Functional testing | 1 hour | | Total for Intelligent Viewing | About 7 to 8 hours |

The estimate excluded the client's own time to bring up the replicated servers.

What I learned

Disaster recovery is an architecture question before it is an infrastructure task. The useful contribution was not configuring servers but noticing which parts of production the plan had quietly left out, and turning that into a checklist people could act on.
