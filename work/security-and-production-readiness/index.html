Case study 06 of 06

Security and production-readiness findings

postMessage origin validation, token refresh, authorisation header propagation, CORS and viewer asset authorisation in a React and document-viewer integration.

  • Security
  • VAPT
  • Auth

Context

An enterprise React application integrated with a document-viewing platform has to do more than render documents. Authentication tokens, cross-origin requests, messages between the application and the embedded viewer, and authorisation of viewer assets all have to be right before the integration is production-ready, and vulnerability assessment and penetration testing will check them.

I investigated these areas as part of the Intelligent Viewing integration and its production readiness. Where an item below led to a change, it was implemented as part of the integration work; where it was an investigation or a proposal, it is described as one.

What I looked at

  • postMessage origin validation. Messages between the host application and the embedded viewer must check their origin, so that a page in another origin cannot drive the viewer or read its responses.
  • Command idempotency. Whether repeated viewer commands, for example from retries, could produce duplicate or inconsistent state.
  • Token refresh. How OTDS tokens were cached and refreshed, and what happened when a token expired mid-session.
  • Race conditions. Ordering between viewer initialisation, token availability, and the first authenticated request.
  • Authorisation header propagation. Which viewer requests carried the authorisation header and which did not, which is how the missing header on asset service requests was found.
  • CORS configuration. What the browser would and would not allow between the application origin and the viewer services.
  • Viewer asset authorisation. Whether assets served for a document could be fetched without the right credentials.
  • Secure communication between the front end and the document services as a whole.

What went wrong and how it was found

The concrete defect found in this review was the missing authorisation header on asset service requests, traced by watching the viewer's outgoing requests and comparing which ones carried credentials. It was fixed as part of the integration. The remaining items were investigated and documented so that the production configuration and the testing scope could cover them.

What I learned

Security review of an integration is mostly about the seams: the message channel between host and embedded viewer, the token lifecycle, and the headers on every request type. Each seam is small, and each is where a production application is most likely to be caught out.
