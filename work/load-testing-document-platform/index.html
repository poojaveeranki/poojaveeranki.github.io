Load testing a document-viewing platform

Running k6 and Playwright tests at increasing concurrent-user levels and relating response times to Publisher capacity and server resources.

  • k6
  • Playwright
  • Nginx
  • Capacity

Context

The Intelligent Viewing platform described in the integration case study had to hold up under real concurrent use, not just return successful responses for one user. Nobody knew how many simultaneous users the environment could serve before document publishing slowed down or services became unstable.

Load testing and the high-availability work that followed were my own work.

What I did

  • Wrote and ran k6 load-testing scripts against the platform, and used Playwright to drive realistic browser-level flows through the viewer.
  • Tested virtual-user levels from 10 up to 100 concurrent users, measuring HTTP request duration and watching service behaviour.
  • Watched server-side resources, Nginx and back-end service errors, and application logs during each run.
  • Evaluated how increasing the number of Publisher instances affected throughput and memory.
  • Implemented and troubleshot Nginx load balancing in front of the publication, asset, markup, search and viewer services, with multiple publication service instances behind the upstream.

What went wrong and how it was found

| Run | What happened | | --- | --- | | 50 virtual users, 5 minutes | Checks passed, response times acceptable | | 100 virtual users, 10 minutes | Significant degradation | | 100 virtual users | Average response about 15.6 s, median 14.3 s, maximum 42 s |

The UAT environment handled roughly 40 concurrent users reliably before response times climbed.

Adding Publisher instances did not simply scale. Two Publisher instances were stable on a 16 GB virtual machine. Going beyond two caused memory starvation, so the number of publishers had to be balanced against the memory actually available.

Along the way I also worked through RabbitMQ service problems, SQL Server memory pressure, licence failures, disk space and Windows paging-file issues. One Publisher refused to start because of a port conflict on its ZeroMQ bridge, which was resolved by changing the configured IPC port.

What I learned

The bottleneck was not the viewer or the network but document conversion capacity, and conversion capacity was bounded by memory on the host. A load test is only useful if you can connect the response-time curve to the resource that is actually saturating.
